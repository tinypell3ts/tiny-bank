# AGENTS.md

Guidance for AI coding agents (and humans) working in this repo. Nested `AGENTS.md` files in subfolders add local rules. The nearest one wins for its folder.

## Project purpose

tiny-bank is a core banking platform made of Go microservices, with Postgres for storage and Kafka for events. Code should be clear and easy to read. Correctness of money handling matters more than features.

The target runtime is **Docker on Kubernetes**: a local kind cluster, services deployed with Helm, the dev loop run by Tilt, Postgres via CloudNativePG, and Kafka via Strimzi. See [docs/architecture.md](docs/architecture.md).

## Working agreement

- Work in **small phases**. Each phase is one PR, split into several small commits. The plan lives in [docs/phases/](docs/phases/).
- **Agents never run git write commands.** Do not create branches, commit, push or tag. Write the files, explain them, and suggest how to commit them. The human runs git. Agents open or edit a PR only when the human asks (see [Pull requests](#pull-requests)).
- After each step: give each commit as a `git add -A -- <paths>` command followed by its Conventional Commit message (`-A --` stages deletions too), explain the concepts and why, give a verify command, then **stop for questions**.
- **A PR is not done without tests and docs.** New code gets tests. Changed behaviour gets updated docs (README, `docs/`, ADRs, and `AGENTS.md` if layout or commands change).

## Branches — Conventional Branch

Format `<type>/<description>`, trunk is `main`.

- Types: `feature/` (alias `feat/`), `bugfix/` (alias `fix/`), `hotfix/`, `release/`, `chore/`.
- Lowercase `a-z`, `0-9` and hyphens only. Dots are allowed only in release versions (`release/v1.2.0`). No leading, trailing or repeated hyphens or dots.
- Optional ticket ref: `feature/issue-12-ledger-postings`.
- Examples: `feature/phase-0-foundations`, `chore/bump-go`.
- **Never use vendor or agent prefixes** such as `claude/`, `copilot/` or `codex/`.
- **This is deliberately stricter than the published spec** ([conventionalbranch.org](https://conventionalbranch.org)), which allows dots in any branch, AI-agent types like `claude/`, and any description after `release/`. We allow dots only in versions, ban agent types, and require `release/` to be a version. The rule lives in `scripts/check-branch-name.sh`, which `scripts/check-branch-name_test.sh` tests.

## Commits — Conventional Commits

`<type>(<scope>): <summary>`, for example `feat(ledger): add posting`, `docs(adr): record typhon decision`, `chore: add gitignore`.
Types: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`, `ci`, `build`, `perf`.

**No AI attribution, anywhere.** Commit messages, PR descriptions, review-thread replies, code and docs never mention Claude, an AI assistant or "generated by", and commits carry no `Co-Authored-By` trailer for one. End a commit message at its description, a PR body at its checklist, and a thread reply at its explanation.

## Pull requests

- **Open a PR only when the human asks**, after they've pushed the branch. Open it as a **draft**, assigned to its author, with labels:

  ```bash
  gh pr create --draft --assignee @me --label "enhancement,area: ledger" --title "…" --body-file …
  ```

  Never mark it ready for review yourself. The human does that once the whole piece of work is pushed, and that's when Greptile reviews.
- **Labels:** a type label from the PR title's Conventional Commit type, plus an `area:` label for each part the PR changes.
  - Type: `feat` → `enhancement`, `fix` → `bug`, `docs` → `documentation`. The other types (`refactor`, `test`, `chore`, `ci`, `build`, `perf`) get no type label: the title already says what kind of change it is. Add `security` to any PR that changes a security control, a known gap or `docs/security.md`.
  - Area: `area: ledger`, `area: account`, `area: kit`, `area: db`, `area: money`, `area: proto`, `area: observability`, `area: deploy`, `area: ci` (GitHub Actions, the Makefile, `scripts/`). A new service gets its own `area:` label, created with the service. A PR that only changes repo-wide files (`README.md`, `AGENTS.md`, `.github/` templates) gets no `area:` label.
- **The description** follows [the template](.github/pull_request_template.md), in plain language. Keep it current, unasked, after each step is pushed: what's done and what's next, the "How to review" table (one row per commit, what to read closely, what to skip), and the "How to check it works" commands. Use code paths, not relative links: in a PR description they resolve against the PR's own URL.
- **Greptile gates each push once the PR is ready.** After each push, check its review and any unresolved threads (`reviewThreads` and `isResolved` in the GraphQL API). Fix the valid findings, and once the human has pushed the fix, reply to each thread naming the fix commit and how it was tested, then resolve it. Don't start the next step while a review is pending or a thread is open.

## Describing the project

Describe tiny-bank as a core banking platform. In README, `AGENTS.md`, docs, ADRs and PR descriptions, don't present it as a copy or "<company>-style" version of another bank, or as a learning or demo project. Using other companies' open-source packages (Typhon, terrors), designs like theirs, and crediting them in code, `go.mod` and ADRs is fine. Explaining concepts in the phase pages is fine too.

├── cmd/hello/           # demo service: the smallest service built on pkg/kit
├── cmd/account/         # account service binary: its migrations and routes, run by db.Run
├── cmd/ledger/          # ledger service binary: its migrations and routes, run by db.Run
├── services/account/    # account service code: domain, Postgres store, HTTP API, migrations/*.sql
├── services/ledger/     # ledger service code: double-entry journals, balances under row locks, idempotency keys, migrations/*.sql

│   └── kittest/         # Conformance: the checks every service's handler must pass (health, request IDs, errors, metrics); ConformanceOf runs them on a service's routes; Start runs a service for integration tests
├── pkg/obs/             # shared observability: Prometheus registry, /metrics handler, HTTP RED metrics (Track)

│   └── dbtest/          # StartPostgres for integration tests (testcontainers)
├── pkg/money/           # Money (int64 minor units + Currency): Add/Sub that never mix currencies or overflow
├── proto/               # protobuf contracts (buf), one versioned package per service API, plus generated Go
├── deploy/
│   ├── kind/            # local kind cluster config
│   ├── charts/service/  # ONE generic Helm chart used by every service
│   ├── cnpg/            # CloudNativePG operator values (Postgres for services)
│   ├── monitoring/      # kube-prometheus-stack values + dashboards/*.json (Grafana) for the local cluster
│   └── values/          # one values file per service (hello.yaml, …)
└── docs/
    ├── architecture.md  # evolving architecture diagram
    ├── observability.md # logs, metrics, traces — what exists and why

Each service is a binary in `cmd/<name>/` (wiring only) plus its code in `services/<name>/`. A service's API is a protobuf contract in `proto/<name>/v<N>/`.

Nested rules: [deploy/AGENTS.md](deploy/AGENTS.md) for the cluster, chart and dev loop, and [pkg/kit/AGENTS.md](pkg/kit/AGENTS.md) for changing the shared foundation, and [proto/AGENTS.md](proto/AGENTS.md) for changing contracts.

## Commands

```bash
make             # list targets
make fmt         # format code
make check       # everything CI runs: fmt-check, vet, lint, test (-race -cover), test-scripts, proto-check
make test-integration # integration tests against real Postgres in Docker (CI runs these too)
make proto       # regenerate Go from proto/ after changing a .proto file (needs buf)
make proto-check # contracts: buf format and lint, no breaking changes against main, generated Go up to date
make hooks       # once per clone: enable the pre-push branch-name check
make docker-smoke             # build the hello image and smoke-test it
make docker-smoke SERVICE=x   # same for cmd/x
make cluster-up               # create the local kind cluster "tiny-bank" (no-op if it exists)
make image-load               # build IMAGE and load it into the cluster
make cluster-down             # delete the cluster
make deploy                   # build SERVICE (default hello) and helm-install exactly that build (needs make monitoring first)
make undeploy                 # helm-uninstall SERVICE (deletes its database and data too)
make chart-check              # helm lint + kubeconform (incl. CRD schemas) for every deploy/values/*.yaml and chart ci/*.yaml
make monitoring               # install or upgrade Prometheus + Grafana in namespace "monitoring" (make dev does this)
make monitoring-down          # remove the monitoring stack
make cnpg                     # install or upgrade the CloudNativePG operator in "cnpg-system" (make dev does this)
make cnpg-down                # remove the operator (CRDs and databases stay)
make dashboards               # reload deploy/monitoring/dashboards/*.json into Grafana (Tilt does this on save)
make dashboards-check         # validate the dashboard JSON (CI runs this)
make dev                      # day-to-day: Tilt builds, deploys and port-forwards everything, redeploys on save
make load-journals RATE=5 DURATION=1m # with make dev running: post random journals to the ledger, then print a summary
make dev-down                 # remove what Tilt deployed, INCLUDING every service database and its data (cluster, monitoring, CloudNativePG stay)
```

Use `make dev` for everyday work, and `make deploy` for a one-off deploy without Tilt. Don't mix them for the same service: both create the same resources. A new service needs one `go_service(...)` line in the `Tiltfile`, with its own localhost port. Ports 8080 (hello), 8081 (account), 8082 (ledger), 3000 (Grafana) and 9090 (Prometheus) are taken.

`make deploy` tags each build `build-<hash of the image's layers>`, so unchanged code means no restart and changed code means a rollout. Never deploy a fixed tag like `:dev`, because Kubernetes can't tell it changed.

Cluster commands use the kubectl context `kind-tiny-bank`. Always pass `--context kind-tiny-bank` in scripts and docs, so nothing ever runs against another cluster by accident.

To look inside a service's database, run `kubectl --context kind-tiny-bank exec -it <name>-db-1 -c postgres -- psql app` (for the account service, `account-db-1`; for the ledger, `ledger-db-1`). Its tables are the service's migrations, in `services/<name>/migrations/`. Only read, unless the human asks you to change data.

**When debugging, look before you change anything, and never destroy data to fix a problem.** `make dev-down`, `make undeploy`, `make cluster-down` and deleting a database `Cluster` or its PVC all delete every account in it. Ask the human first, even if starting over looks like the quickest fix.

Run `make check` before handing work back. CI (`.github/workflows/ci.yml`) runs the same targets on every PR, plus a `branch-name` job.

## Conventions

- **Money is `int64` minor units plus an ISO 4217 currency code**, always as `money.Money` from `pkg/money` ([ADR-0004](docs/adr/0004-represent-money-as-int64-minor-units.md)). Never use floats for money, never mix currencies silently, and always handle the error from `Add`/`Sub`. Never discard it with `_`: lint doesn't catch that, so reviewers must.
- **Every service is built on `pkg/kit` and [Typhon](https://github.com/monzo/typhon):** `kit.Main`, `kit.LoadConfig` (embed `kit.Config` for extra settings), `kit.NewLogger` and `kit.Serve`. A service with its own database is just `var run = db.Run(name, migrations, routes)` and `kit.Main(name, run)`: `db.Run` loads config, builds the routes (they must only keep the pool, not query it, so a bad setting stops the service before it waits for a database), waits for the database and migrates it (`db.Start`), and only then listens and serves. `routes(router, deps)` builds the API from `db.Deps`: the pool, `Getenv` for settings of the service's own (the ledger's `ACCOUNT_URL`) and `Metrics` for its business metrics. It returns an error if a setting is missing, so the service refuses to start. `kit.Handler` adds `/healthz` and `/readyz` itself (readiness checks the database), so a service never writes probes. Routes are a `typhon.Router` of `typhon.Service` handlers, and `kit.Handler` wraps it in the shared filters: request IDs, access logs, metrics, error cleaning and panic recovery. Handlers fail by returning a [terrors](https://github.com/monzo/terrors) error (`terrors.BadRequest("holder_name", "…", nil)`, `terrors.NotFound(…)`), read a request into its proto message with `kit.Decode`, and answer with `kit.Respond` or `kit.RespondCreated`. A service calls another with `kit.Get` or `kit.Post`, never Typhon's client directly, so every call is binary protobuf, passes the request ID on, has a timeout and keeps transport errors. A `kit.Post` that times out may or may not have been acted on, so only post what has an idempotency key, and retry with the same key. Where another service is comes from an env setting (`ACCOUNT_URL=http://account`, the other service's name), and its errors are never passed on to your own callers as they are: turn the ones you expect into your own terrors, and anything else into a 500. Bodies are JSON with the proto field names (`customer_id`). `kit.Decode` is strict: one JSON object, or binary protobuf, with no unknown fields or enum values, at most 16 KB (`kit.Handler` caps every body), and every failure is a 400 with its own code. Any other error is logged and hidden from the caller as a 500, and a caller that hangs up gets 499. A service only writes its own routes and wiring. Never copy the filters into a service. Every service has a `TestConformance` that runs `kittest.ConformanceOf` on its routes, and its own tests cover only what's its own.
- **Config from environment variables** (12-factor). No config files baked into images.
- **Logs are structured JSON to stdout** via `log/slog`. Never log secrets or full card or account numbers.
- **Metrics come from `pkg/obs`.** `kit.Handler` serves `GET /metrics` and records HTTP metrics for every service. Metric labels must have a small, fixed set of values: use route patterns (`/accounts/:id`), never raw paths, IDs, emails or amounts.
- **Kubernetes-ready from day one:** expose `/healthz` (liveness) and `/readyz` (readiness), shut down gracefully on `SIGTERM`, and keep no local file state.
- **Errors:** wrap with context (`fmt.Errorf("open account: %w", err)`). Never leak internal errors to API clients. Never put secrets, tokens or personal details in an error: when a request fails, `pkg/kit` logs the full error, because it's the only record of why.
- **Secrets are `kit.Secret`.** Every secret read from the environment (like `DATABASE_URL`) is stored as a `kit.Secret`. It prints as `xxxxx` everywhere (fmt, slog, errors, JSON), so logging a config can't leak it. Call `.Reveal()` only where the value is used, such as `db.Open`, never to log or return it. Why this beats redacting logs: [ADR-0008](docs/adr/0008-stop-secrets-where-they-enter.md).
- **terrors travel between services.** Typhon sends an error's code, message and params to the calling service ([ADR-0007](docs/adr/0007-build-services-on-typhon-and-terrors.md)). Never put secrets, passwords, tokens or personal details (names, emails, full account numbers) in a terror's message or params. To check a terror that may be wrapped, find it with `errors.As(err, &terr)` first: `terrors.PrefixMatches(err, …)` and `terrors.Is` don't look inside `fmt.Errorf("…: %w")`.
- **Tests:** table-driven where it fits. Standard library `testing` first. Tests that need a real dependency (Postgres) go in `*_integration_test.go` files tagged `//go:build integration`, and start it with testcontainers. `make check` skips them; `make test-integration` and CI run them.
- **Databases:** connect with `db.Open` from `pkg/db`, using `DATABASE_URL` from the environment. Never build connection strings by hand, and never log `DATABASE_URL` itself (errors from `db.Open` are safe to log).
- **Migrations** are goose SQL files (`<version>_<name>.sql`) embedded in the service and applied at startup with `db.Migrate`, before the service reports ready ([ADR-0005](docs/adr/0005-run-migrations-at-startup-behind-an-advisory-lock.md)). Every migration must work with the code that is already running (expand, then contract). Never edit a migration that has been applied anywhere; fix forward with a new one.
- **One Go module** for the monorepo, so every service always builds against the latest shared code.
- **Bump Go in three places together:** `go.mod`, `GO_VERSION` in the `Dockerfile`, and the golangci-lint version in CI, which must be built with a Go version at least as new.
- **Images** are distroless and run as non-root. Never add a shell or package manager to the runtime stage.

## Security

tiny-bank handles money and personal data, so these rules apply to every change. The Conventions above on secrets, logs, errors, terrors and images are security rules too. [docs/security.md](docs/security.md) explains what each control protects against and which gaps are still open. Read it before working on anything that touches access, input handling, secrets or the deployment.

- **Nothing is reachable from outside the cluster until Phase 12.** There's no sign-in yet: any caller that can reach a service can open an account for any customer and read any account. So every service stays a `ClusterIP` Service. Never add an Ingress, a `NodePort` or `LoadBalancer` Service, or a `hostPort`, and never widen a `kubectl port-forward` beyond localhost.
- **Personal data stays out of side channels.** Holder names, customer IDs and anything a customer types never go in metric labels, terror messages or params, or error text. Account IDs are random UUIDs, not bank account numbers, so they may appear in paths and logs.
- **Caller input never becomes SQL.** Queries pass every value as a parameter (`$1`). Never build SQL from caller input, even after validating it.
- **Turn caller input into typed values at the edge.** Handlers parse text into `uuid.UUID` (with `kit.ParseUUID`), `money.Currency` and checked domain types before anything else uses it, and accept only canonical forms, so one account has one URL.
- **Never weaken a check to get green.** Don't loosen a validation, delete or skip a failing test, add a `nolint`, or drop a CI step to make something pass. Fix the cause, or stop and ask.
- **Anything that moves money is idempotent** (from Phase 7): the same request sent twice moves money once.
- **New dependencies are a security decision.** Add one only when the standard library or an existing dependency can't do the job, say why in the PR, and pin it in `go.mod`.
- **Stop and ask the human before changing** `kit.Handler`'s filters (error cleaning above all), `kit.Secret`, `kit.Decode`'s limits, the pod security settings in `deploy/charts/service/templates/deployment.yaml`, or anything that changes what can reach a service.
- **Found a vulnerability while working? Tell the human straight away**, and don't put the details in a public issue, PR or commit message ([SECURITY.md](SECURITY.md)).
- **Keep [docs/security.md](docs/security.md) true, in the same PR.** It goes stale most often through code and deploy changes, not docs. If a change touches a control, a known gap, or a file either one links to, update that row. Closing a gap moves it to the controls table, and a new control gets a row. An ADR states its security impact in its Security section ([template](docs/adr/template.md)). A security choice with real alternatives, such as how secrets are kept out of logs, gets its own ADR; a plain rule belongs here instead.

## Engineering principles

- **DRY:** a concern used by two or more services lives in `pkg/*`, never copy-pasted. Rule of two: duplicating once is fine, extract on the second use.
- **KISS:** the simplest thing that works. Standard library before third-party libraries. Readable beats short.
- **YAGNI:** build only what the current phase needs. No speculative config flags, and no interfaces with one implementation unless a test needs them.
- **Tension rule:** YAGNI beats DRY for premature abstraction. Shared platform code (`pkg/kit`) only grows when its first real consumer arrives.
